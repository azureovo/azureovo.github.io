📋 摘要

报告核心问题：3DGS 在 Unity 游戏引擎中能承担哪些场景表达任务，不能承担哪些？

3D Gaussian Splatting（3DGS）作为一种新型显式点云场景表示方法，在实时新视角合成、真实场景重建与轻量化可视化方面表现出较强能力。然而，游戏引擎不仅需要"看起来真实"的场景，还需要物理碰撞、动画系统、资源流式加载、编辑器工作流和跨平台部署等完整工程能力。 本报告基于个人在 Web 端 3DGS 展示、Unity 端 3DGS 渲染 和 Three.js 游戏交互环境 三方面的实践，围绕"3DGS 在 Unity 游戏引擎中的应用边界"展开调研与验证。报告明确指出： 3DGS 更适合作为游戏中非核心复杂场景的视觉代理，而非完整替代 Mesh 管线；并提出了"3DGS 视觉层 + Mesh 物理代理 + 分离管线 + Web 原生渲染"的可行 Pipeline。

🔑 核心发现

基于三线 Demo 实践与工具链验证的六点关键结论

🎯

定位：视觉代理而非 Mesh 替代

3DGS 不适合直接替换完整 Mesh 管线——无连续表面、无法原生碰撞、无法动态响应光照。其正确定位是 非核心复杂场景的静态视觉层，物理/动画/碰撞由传统 Mesh 承接。

⚠️

Unity WebGL 是最大工程瓶颈

实测 URP Shader 变体打包后超 70GB，WebGL 构建直接失败。Compute Shader 依赖 OpenGL ES 不支持的 GPU 特性，Unity Editor 能跑 ≠ WebGL 能发布。

🌐

Web 原生 3DGS 已落地验证

Web Demo 页已稳定承载 15 个 DL3DV/RE10K 场景，支持 FPV 漫游、多机器人（Humanoid/Dog/Rover）添加、位置标记等交互，浏览器端实时渲染帧率达 30-60 fps。

🦴

视觉-物理分离架构已工具化

CloudCompare PoissonRecon → Blender 减面 → Unity Collider 的工具链已验证：两千万高斯点 → 3MB 碰撞体，满足 Web/移动端物理交互的轻量化需求。

👥

多人联机已通过 Firebase 验证

Three.js 游戏页面已实现 glTF + 3DGS 双场景下的 实时多人在线同步，基于 Firebase Realtime Database，验证了 3DGS 场景在社交互动场景中的可行性。

📊

产品化路径优先级明确

P0 短视频 3D 背景 → P1 虚拟展馆 & 社交空间 → P2 UGC 场景生成工具链。从"能看"到"能交互"再到"能创作"，逐级验证产品价值。

⚡ 核心技术挑战

从工程实践中识别的 6 大关键瓶颈，含已验证方案与推荐对策

  • 1

    渲染后端断层：桌面 vs Web

    桌面端依赖 DX12/Compute Shader 高效渲染高斯泼溅，但 WebGL (OpenGL ES 子集) 不支持 Compute Shader。结论：桌面用 Unity，Web 用 Three.js / WebGPU 原生管线，不试图将同一套渲染代码同时发布到两个平台。

  • 2

    Shader 变体爆炸：构建不可控

    URP + 3DGS 自定义 Shader 产生海量 Variant 组合，实测 packing 阶段提示 preparing variants (1510M / 72477M)，导致 WebGL 构建体积和时间完全失控。对策：精简 URP Feature · Shader Stripping 剔除无用 Keyword · 为 Web 独立维护最小渲染工程而非复用完整 URP 管线。

  • 3

    资产管线断裂：格式鸿沟

    3DGS 以 .ply / .splat / .spz 格式存储高斯参数（位置/协方差/球谐/不透明度），Unity 原生不识别。缺乏 Importer、Prefab 化、LOD 生成、AssetBundle 打包等标准资产工具。需自建导入器 + 压缩工具 + 运行时 Loader，方能融入 Unity 生产管线。

  • 4

    碰撞与物理：点云无表面

    3DGS 本质是离散高斯椭球体集合，无 Mesh 拓扑概念，无法直接生成 Collider。已验证方案：点云 → CloudCompare PoissonRecon 建面 → Blender 减面 → Unity Mesh Collider。2000 万高斯点场景生成碰撞体仅 3MB，远小于原始点云 37MB。

  • 5

    光照一致性与动态场景

    3DGS 的光照/颜色信息已烘焙在训练结果中（球谐系数），无法如 PBR 材质般实时响应场景动态光源。此外，形变/破碎/角色动画等动态需求需 4DGS 或物理仿真扩展，计算开销远超当前轻量化目标。短期定位：静态场景视觉层。

  • 6

    包体与跨平台部署压力

    单个中等规模 3DGS 场景约 30-40MB (.splat)，面对 Web 首屏和移动端小游戏场景，加载压力显著。对策：SPZ 量化压缩 · 分块流式加载 (tile streaming) · LOD 渐进细化 · 按需剔除。需配合 CDN 分发策略和 AssetBundle 增量更新机制。

💡 结论

  • 3DGS 在非核心复杂场景的视觉表达上具有明确价值，适合承担远景、背景、虚拟展馆、视频背景和关联视觉代理
  • Unity Editor 桌面端 3DGS 渲染性能基本达标，但 Unity WebGL 因 Shader 变体爆炸和 Compute Shader 后端限制，暂不适合作为短期线上化主路线
  • 3DGS 不应被定位为 Mesh 的完整替代，而应采用"3DGS 视觉层 + Mesh 物理代理 + 传统动态对象"的混合架构。已验证：通过 CloudCompare PoissonRecon 可将两千万高斯点建面为仅 3MB 的轻量碰撞体，经 Blender 中转即可进入 Unity 物理管线
  • 面向抖音社交与娱乐场景，短视频 3D 背景、虚拟展馆和轻量小游戏场景生成是比"完整 3DGS 游戏"更现实的产品落地方向
  • 总体而言，3DGS 在游戏中的短期价值是提供一种高真实感、低建模约束的静态视觉代理，让开发者更快地将真实世界或复杂场景带入交互式应用
