📋 摘要

报告核心问题：3DGS 在 Unity 游戏引擎中能承担哪些场景表达任务，不能承担哪些？

3D Gaussian Splatting（3DGS）作为一种新型显式点云场景表示方法，在实时新视角合成、真实场景重建与轻量化可视化方面表现出较强能力。然而，游戏引擎不仅需要"看起来真实"的场景，还需要物理碰撞、动画系统、资源流式加载、编辑器工作流和跨平台部署等完整工程能力。 本报告基于个人在 Web 端 3DGS 展示、Unity 端 3DGS 渲染 和 Three.js 游戏交互环境 三方面的实践，围绕"3DGS 在 Unity 游戏引擎中的应用边界"展开调研与验证。报告明确指出： 3DGS 更适合作为游戏中非核心复杂场景的视觉代理，而非完整替代 Mesh 管线；并提出了"3DGS 视觉层 + Mesh 物理代理 + 分离管线 + Web 原生渲染"的可行 Pipeline。

🔑 核心发现

四点关键结论，定义了 3DGS 在游戏引擎中的真实定位

🎯

定位：视觉代理，非 Mesh 替代

3DGS 不应被简单理解为"取代 Mesh"，而应放置在具体游戏开发流程中讨论。其短期价值是 充当复杂场景的视觉代理，物理、动画、碰撞仍由传统 Mesh 承担。

⚠️

Unity WebGL 是最大瓶颈

URP Shader Variant 爆炸导致 WebGL 构建失败，Compute Shader 依赖使其难以跨平台。Unity Editor 能跑 ≠ Unity WebGL 能发布。

🌐

Web 原生渲染是更优路径

对于 Web 端轻量化产品，Three.js / WebGPU 或专用 3DGS 渲染器可能比 Unity WebGL 更适合作为短期落地技术路线。

🏗️

"视觉与逻辑分离"架构

可行 Pipeline 的核心思路是：3DGS 负责视觉呈现，Mesh Proxy 负责物理交互，两者协同而非互相替代。

⚡ 核心技术挑战

6 大关键瓶颈及其影响范围与建议对策

  • 1

    渲染后端不兼容

    Unity WebGL 无法复用桌面端 Compute Shader 管线。桌面用 Unity，Web 端用 Three.js / WebGPU 原生渲染器。

  • 2

    Shader 变体爆炸与构建不可控

    URP 产生亿级 Variant 导致构建时间、体积和内存失控。精简 URP 设置 + Shader Stripping + 独立渲染工程。

  • 3

    资产生态与编辑器工具缺失

    3DGS 以 .ply/.splat 格式存储，Unity 无法原生理解。需设计自定义 Importer、压缩工具和运行时 Loader。

  • 4

    碰撞与导航系统缺失

    3DGS 无连续表面，无法直接用于精确碰撞。已验证方案：将点云导入 CloudCompare，使用 PoissonRecon 工具计算建面输出 Mesh，经 Blender 中转格式后导入 Unity。实测两千万个高斯点的场景，生成的碰撞体仅 3MB，完全满足轻量化需求。采用低模 Mesh Collider 作为物理代理，3DGS 仅负责视觉。

  • 5

    动态场景与光照一致性

    3DGS 的光照信息通常烘焙在训练结果中，无法自然响应游戏动态光源。短期内限定为静态视觉层。

  • 6

    包体与加载压力

    30-40MB 的单个 3DGS 场景在 Web/小游戏场景下首屏压力大。SPZ 压缩 + 分块流式 + LOD 渐进加载。

💡 结论

  • 3DGS 在非核心复杂场景的视觉表达上具有明确价值，适合承担远景、背景、虚拟展馆、视频背景和关联视觉代理
  • Unity Editor 桌面端 3DGS 渲染性能基本达标，但 Unity WebGL 因 Shader 变体爆炸和 Compute Shader 后端限制，暂不适合作为短期线上化主路线
  • 3DGS 不应被定位为 Mesh 的完整替代，而应采用"3DGS 视觉层 + Mesh 物理代理 + 传统动态对象"的混合架构。已验证：通过 CloudCompare PoissonRecon 可将两千万高斯点建面为仅 3MB 的轻量碰撞体，经 Blender 中转即可进入 Unity 物理管线
  • 面向抖音社交与娱乐场景，短视频 3D 背景、虚拟展馆和轻量小游戏场景生成是比"完整 3DGS 游戏"更现实的产品落地方向
  • 总体而言，3DGS 在游戏中的短期价值是提供一种高真实感、低建模约束的静态视觉代理，让开发者更快地将真实世界或复杂场景带入交互式应用
